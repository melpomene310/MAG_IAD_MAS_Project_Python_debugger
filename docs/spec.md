# Спецификация проекта «LLM-отладчик Python-программ (ConDefects)»

Подробная спецификация: форматы данных, метрики, протокол экспериментов. Краткие правила работы — в [AGENTS.md](../AGENTS.md).
Если код расходится с этим файлом, исправьте код или осознанно обновите файл.
Введение для новых участников — в [README.md](../README.md).

---

## Коротко о проекте

- Есть Python-программа с одной логической ошибкой и набор тестов к ней.
- Языковая модель (LLM) должна исправить программу так, чтобы прошли **все** тесты.
- Мы сравниваем несколько способов организовать работу модели (их называем **решателями**)
  на одних и тех же задачах и при одинаковых условиях.
- На выходе — отчёт: сколько задач решил каждый вариант и сколько это стоило.

Термины (попытка, шаг, инструменты, песочница, вердикты, бины, выборки и т. д.) объяснены
в словарике в [README.md](../README.md#словарик).

## 1. Суть проекта

Учебный проект по курсу «Мультиагентные системы». Система на основе LLM находит и
исправляет логическую ошибку в небольшой Python-программе — решении задачи с AtCoder.
Для этого она может запускать тесты и смотреть значения переменных.

Сравниваем варианты:

| Вариант | ID решателя | Как работает |
|---|---|---|
| Простое решение | `workflow` | Порядок действий жёстко задан в коде: модель получает код и упавшие тесты → возвращает исправленный код → программа прогоняет тесты → если не прошло, модель получает новый отчёт и пробует снова. Модель сама ничего не выбирает и инструменты не вызывает |
| LLM-only | — | Первая попытка `workflow`: один запрос к модели без обратной связи. Отдельно не запускается, считается из результатов `workflow` (раздел 10) |
| Одиночный агент | `single_agent` | Одна модель в цикле сама решает, какие инструменты вызвать (тесты, запуск на своём входе, трассировка) и когда сдать ответ |
| Последовательная MAS | `mas_sequential` | Исследователь локализует ошибку, исправитель предлагает код, проверяющий запускает тесты и возвращает результат. Реализована |
| Конкурирующая MAS | `mas_competitive` | Два независимых исследователя изучают задачу разными методами; арбитр выбирает обоснованную гипотезу, затем выполняются исправление и проверка. Пока не реализована |

**Что видит решатель** (как у авторов ConDefects): программу с ошибкой и **все тесты**
задачи — входы, правильные ответы и результат каждого теста на исходной программе.
Условий задач нет: что должна делать программа, понятно только из тестов.

**Задача решена**, если исправленная программа проходит **все тесты**.

## 2. Порядок реализации

Этапы делаются по порядку. Этап готов, только когда выполнен его критерий.

| # | Этап | Критерий готовности |
|---|---|---|
| 0 | Окружение: Docker, compose, Makefile, `.env`, конфиг (раздел 3) | `make build && make test` проходит на тестовых фикстурах |
| 1 | Данные: загрузка, нормализация, проверка (раздел 4) | `make data` создаёт `data/processed/`, в отчёте видно, сколько задач отброшено и по каким причинам |
| 2 | Разбиение на выборки (раздел 5) | `make split` создаёт списки задач в `splits/`; тесты на повторяемость и непересечение проходят |
| 3 | Песочница, сравнение ответов, трассировка (раздел 6) | Тесты проходят: бесконечный цикл, исключение, память, потоки, `exit()`, вещественные числа |
| 4 | LLM-клиент с кэшем и подсчётом токенов (раздел 7) | Тесты с фейковым сервером проходят, кэш работает, токены считаются и для неудачных запросов |
| 5 | Решатель `workflow` (раздел 8.1) | `make smoke SOLVER=workflow` на фикстурах с фейковой LLM даёт корректный `tasks.jsonl` |
| 6 | Инструменты и решатель `single_agent` (разделы 8.2, 8.3) | `make smoke SOLVER=single_agent` проходит; ошибки вызова инструментов и лимиты обработаны |
| 7 | Запуск экспериментов, метрики, отчёт, разбор задач (раздел 10) | `make report` строит `report.md` со всеми разделами из 10.3 |

Статус: этапы 0–7 реализованы. Для этапов 1–2 на реальных данных нужны тесты из
`make fetch-tests` или архив `Test.zip` (раздел 4.1).

## 3. Окружение и запуск

### 3.1. Docker

Один образ на основе `python:3.11-slim` (эта версия Python используется на AtCoder с 2023 года).
Внутри **два независимых интерпретатора Python**:

- **Для приложения** — виртуальное окружение `/opt/venv`, зависимости из `pyproject.toml`
  ставятся через `uv sync --frozen` (точные версии из `uv.lock`).
- **Для песочницы** — системный `/usr/local/bin/python` с библиотеками, как на AtCoder
  (`requirements-atcoder.txt`). Им запускается код из датасета и код от модели. Код
  приложения ему недоступен.

Начальный список `requirements-atcoder.txt`: `numpy`, `scipy`, `networkx`, `sympy`,
`sortedcontainers`, `more-itertools`, `bitarray`, `ac-library-python`, `mpmath`, `gmpy2`,
`pandas`. Список дополняется, если проверка данных находит недостающие библиотеки
(раздел 4.3). Системные пакеты для сборки библиотек ставятся и удаляются в том же слое образа.

`docker-compose.yml` — один сервис `app`:
- `env_file` выбирается через `PROFILE` в Makefile: `.env` по умолчанию,
  `.env.openrouter` или `.env.local` для соответствующего профиля;
- папка проекта смонтирована в `/app` (код, `data/`, `results/` сохраняются на хосте);
- `extra_hosts: ["host.docker.internal:host-gateway"]` — чтобы контейнер видел модель,
  запущенную на хосте.

Команды в контейнере выполняются от root (это нужно песочнице, раздел 6.1). Чтобы файлы на
хосте не становились root-овыми, CLI после каждой команды возвращает их владельцу репозитория.

### 3.2. Настройки: `.env` и YAML-конфиги

Настройки разделены на два вида:

- **Файл окружения** — адрес, модель, ключ и тарифы. `.env` используется по умолчанию;
  `PROFILE=openrouter` выбирает `.env.openrouter`, `PROFILE=local` — `.env.local`.
  Рабочие файлы игнорируются Git; в репозитории есть шаблоны с суффиксом `.example`.
  `pydantic-settings` читает только выбранный файл через `DEBUGMAS_ENV_FILE`.

  ```dotenv
  # OpenAI-совместимый endpoint (удалённый сервис или локальный сервер)
  OPENAI_BASE_URL=http://host.docker.internal:8000/v1
  OPENAI_API_KEY=changeme
  MODEL=deepseek-v4.1-flash

  # Цены за 1M токенов, для подсчёта стоимости (для локальной модели — 0)
  PRICE_INPUT_PER_1M=0
  PRICE_CACHED_INPUT_PER_1M=   # тариф кэшированного провайдером входа; пусто — как обычный вход
  PRICE_OUTPUT_PER_1M=0

  LLM_TIMEOUT_S=300
  LLM_MAX_RETRIES=5
  LLM_MAX_CONCURRENCY=4

  LLM_CACHE_ENABLED=1
  LLM_CACHE_DIR=/app/.cache/llm

  SANDBOX_PYTHON=/usr/local/bin/python
  ```

- **YAML-конфиги в `configs/`** — всё, что относится к эксперименту: выборка, лимиты,
  температура, включённые инструменты. Коммитятся в git.

Если параметр задан в нескольких местах, приоритет такой: аргументы командной строки >
YAML > выбранный файл окружения. Итоговые настройки каждого запуска (без ключей)
сохраняются в папку результатов. Тарифы в профиле OpenRouter нужно заполнить фактическими
значениями до платного запуска; для локального сервера они могут быть нулевыми.
Ключ дискового кэша включает адрес endpoint, поэтому ответы разных профилей не смешиваются.

### 3.3. Команды

Все действия — через `Makefile`. Цели выполняются внутри контейнера.

```bash
make build                         # собрать образ
make shell                         # открыть shell в контейнере
make fetch-tests                   # клонировать ConDefects и скачать тесты AtCoder (на хосте, можно продолжать)
make data                          # загрузить, нормализовать и проверить ConDefects
make split PRESET=paper3           # разбить задачи на выборки
make test                          # ruff + pytest
make lint                          # автоформатирование и автоисправления ruff
make smoke SOLVER=workflow         # прогон на фикстурах с фейковой LLM, без сети
make run CONFIG=configs/workflow.yaml SPLIT=val
make run CONFIG=configs/single_agent.yaml SPLIT=val
make final CONFIG=... RUN_TAG=...  # прогон на закрытой выборке test (раздел 5.3)
make report RUNS="results/<id1> results/<id2>"
make case RUN=results/<id> TASK=<task_id>
```

Под капотом всё вызывает CLI: `python -m debugmas <команда>`.

## 4. Данные

### 4.1. Откуда берём

ConDefects: https://github.com/appmlk/ConDefects. Используем только программы на Python.

- Репозиторий клонируется в `data/raw/ConDefects` на **зафиксированном коммите**
  (хэш в `configs/data.yaml`), чтобы данные у всех совпадали.
- Тесты лежат в большом архиве `Test.zip`, которого нет в git. Два способа получить их:
  - `make fetch-tests` (`scripts/fetch_tests.sh`) — скачивает официальные тесты AtCoder из
    зеркала [conlacda/atcoder-testcases](https://github.com/conlacda/atcoder-testcases)
    (ветка на контест), только для Python-задач ConDefects, в `data/raw/Test/`. Можно
    прерывать и продолжать. Контестов, которых нет в зеркале (на момент написания —
    `abc317`), не будет; их задачи отсеются с причиной `no_tests`. Скрипт сам клонирует
    ConDefects на коммите из `configs/data.yaml`, если клона ещё нет. **Версии тестов пока
    не закреплены** — см. «Известные ограничения» в README;
  - скачать `Test.zip` вручную по ссылкам из README ConDefects в `data/raw/Test.zip`.

  Без тестов `make data` останавливается и пишет, где их взять.
- Сложность задач — в `difficulty.txt`, даты — в `date.txt`.
  Значение `unknown` не преобразуется в число; задача отбрасывается с причиной
  `unknown_difficulty`.
- Реальная структура файлов ConDefects описана в `docs/condefects_layout.md`. Загрузчик
  написан по ней, а не по предположениям.

### 4.2. Формат после обработки

`make data` складывает задачи в `data/processed/` (в `.gitignore`):

```
data/processed/
├── tasks/<task_id>/
│   ├── agent_view.json     # что видит решатель
│   ├── ground_truth.json   # эталон, только для оценки
│   ├── fixed_times.json    # время исправленной версии на каждом тесте
│   └── tests/<test_name>.{in,out}
├── index.jsonl             # строка на задачу: task_id, program_id, difficulty, date, n_tests, флаги
└── validation_report.json  # сколько задач и программ отброшено и почему
```

Для пилота `make data ARGS='--out data/pilot/final --task <task_id> ...'`
проверяет только явно перечисленные задачи и пишет результат в отдельный каталог.
Неизвестный `task_id` считается ошибкой; повторные ID обрабатываются один раз.
Пилотные ID записаны в `splits/pilot/paper3/dev.txt` и исключены из будущих `val` и `test`.

Быстрый пилот записывается в `splits/pilot30/paper3/dev.txt`. Скрипт
`make prepare-pilot30` сохраняет шесть исходных пилотных ID и детерминированно выбирает ровно
10 задач в каждом бине (`seed=42`) из локальных Python-задач с каталогами `in/` и `out/`.
Он запускает только выбранные ошибочные версии, чтобы сохранить начальные результаты; исправленные
версии не запускаются. Обработанные файлы лежат в `data/pilot/pilot30/` и не коммитятся;
manifest добавляется в Git после подготовки.

Структуры описаны в `src/debugmas/data/schema.py`:

```python
@dataclass(frozen=True)
class TestCase:
    name: str
    input_path: Path
    expected_path: Path
    time_limit_s: float          # лимит времени на тест (раздел 4.3)

@dataclass(frozen=True)
class AgentView:                 # всё, что разрешено видеть решателю
    task_id: str
    program_id: str
    code: str                    # программа с ошибкой
    tests: list[TestCase]        # все тесты задачи
    initial_results: list[TestResult]   # результат каждого теста на исходной программе

@dataclass(frozen=True)
class GroundTruth:               # только для eval/ и report/
    task_id: str
    program_id: str
    fault_lines: list[int]       # строки с ошибкой, нумерация с 1
    fixed_code: str
    fixed_line: str              # исправленная строка из разметки
    difficulty: int | None
    date: str | None
```

Чтение и запись `GroundTruth` вынесены в отдельный модуль `data/ground_truth.py`.

### 4.3. Какие задачи берём

1. **Одна программа на задачу.** Если у задачи несколько программ с ошибкой, одна
   выбирается случайно, но воспроизводимо (по seed), среди тех, что прошли проверку.
2. **Программа отбрасывается** (причина пишется в `validation_report.json`), если:
   - программа или исправленная версия не разбирается как Python 3 (например, это Python 2);
   - исправленная версия не проходит хотя бы один тест в нашей среде (например, нужна
     нестандартная проверка ответа или не укладывается во время);
   - исправленной версии не хватает библиотеки — причина `missing_library:<имя>`;
     по этому списку дополняется `requirements-atcoder.txt`;
   - программа с ошибкой проходит все тесты (ошибку тесты не ловят);
   - неизвестна сложность задачи.
3. Для каждой задачи сохраняется время работы исправленной версии на каждом тесте.
   **Лимит времени на тест** при решении: `max(2 с, 3 × время исправленной версии)`.

## 5. Выборки

### 5.1. Бины сложности

Задачи делятся на группы по сложности. Границы задаются пресетами в `configs/splits.yaml`:

```yaml
seed: 42
presets:
  paper3:                    # как в статье ConDefects
    bins: {easy: [0, 400], medium: [400, 1300], hard: [1300, null]}
  fine5:
    bins: {b1: [0, 200], b2: [200, 600], b3: [600, 1200], b4: [1200, 2000], b5: [2000, null]}
  hard_only:
    bins: {medium: [400, 1300], hard: [1300, null]}
sizes:                       # сколько задач брать из каждого бина
  val: 15
  test: 50
  dev: rest                  # все остальные
```

Границы `[low, high)`: нижняя включается, верхняя нет; `null` — без ограничения.
Если в бине не хватает задач, выводится предупреждение, и размеры выборок пропорционально
уменьшаются.

### 5.2. Три выборки

| Выборка | Для чего |
|---|---|
| `dev` | Разработка: отладка кода, настройка промптов, разбор задач. Можно смотреть что угодно |
| `val` | Небольшой общий набор для сравнения вариантов на промежуточных показах. Промпты под него не подгоняются |
| `test` | Закрытая выборка для финальных результатов. На ней ничего не отлаживается |

Разбиение:
- **по задачам** — каждая задача попадает ровно в одну выборку;
- **стратифицированное** — из каждого бина берётся одинаковое число задач;
- **детерминированное** — при том же seed получается тот же результат.
- Задачи пилота из `reserved_dev` в `configs/splits.yaml` остаются в `dev`
  при последующем полном разбиении.

Списки `splits/<preset>/{dev,val,test}.txt` (по `task_id` на строку) **коммитятся в git**,
чтобы у всей команды был одинаковый набор.

### 5.3. Защита выборки `test`

Чтобы финальные цифры были честными:
- `make run` отказывается работать с `--split test`;
- запуск на `test` возможен только через `make final`, который:
  - требует, чтобы все изменения были закоммичены, и записывает коммит в результаты;
  - запрещает фильтры по задачам (`--task`, `--limit`) и подробный вывод (`-v`);
  - отключает кэш LLM;
  - пишет результаты в `results/final/<RUN_TAG>/` и не перезаписывает существующий тег.

## 6. Песочница и инструменты

### 6.1. Запуск кода (`src/debugmas/sandbox/`)

Любой код из датасета и от модели запускается **только** через `sandbox.run_program`:
- отдельный процесс `SANDBOX_PYTHON -I` (изолированный режим), пустое окружение, рабочая
  папка — временная директория с одним файлом программы;
- под root процесс переключается на пользователя `nobody`;
- ограничения через `resource`: время CPU, память (по умолчанию 1 ГБ), размер создаваемых
  файлов, число процессов; плюс таймаут по реальному времени;
- stdout и stderr сохраняются с обрезкой (по умолчанию 64 КБ на поток);
- результат: `stdout`, `stderr`, `exit_code`, `timed_out`, `memory_exceeded`, `wall_time`.

Никаких `exec`/`eval` чужого кода внутри процесса приложения. Тесты задачи прогоняются
параллельно.

### 6.2. Как сравниваем ответы (`sandbox/compare.py`)

- Вывод программы и правильный ответ разбиваются на слова по пробелам и переводам строк
  и сравниваются по словам.
- Если оба слова — числа и хотя бы одно записано с точкой или экспонентой, допускается
  погрешность `1e-6` (абсолютная или относительная).
- Вердикты: `AC`, `WA`, `RE` (ненулевой код возврата), `TLE`, `MLE`.

### 6.3. Трассировка (`sandbox/tracer.py`)

Трассировка — запуск программы, при котором на указанных строках записываются значения
выражений. Работает на стандартном механизме `sys.settrace` и выполняется внутри
песочницы через скрипт-обёртку `trace_harness.py`.

- На входе: код, вход (имя теста или произвольная строка), номера строк, список выражений,
  `max_hits` — сколько срабатываний записать (по умолчанию 30).
- Выражения вычисляются **перед** выполнением строки. Если вычислить не удалось, вместо
  значения записывается ошибка, например `<NameError: ...>`.
- Значения — `repr`, обрезанный до 200 символов.
- Трассируется только файл программы. Поддерживаются потоки (`threading.settrace`);
  `exit()` и исключения программы корректно завершают трассировку.
- Таймаут трассировки — в 5 раз больше обычного лимита теста. При таймауте возвращаются
  уже собранные значения и подсказка взять вход поменьше.

### 6.4. Инструменты для модели (`src/debugmas/tools/`)

Каждый инструмент — функция плюс описание её аргументов (JSON-схема) для tool calling:
модель отвечает не текстом, а вызовом инструмента с аргументами, программа его выполняет
и возвращает результат модели.
Все инструменты регистрируются в `tools/registry.py`; какие из них доступны решателю,
задаётся в конфиге. Ответы — JSON; длинные ответы обрезаются (по умолчанию до 3000
символов) с пометкой `truncated: true` и исходным размером.

| Инструмент | Аргументы | Что возвращает |
|---|---|---|
| `run_tests` | `code?`, `tests?` (по умолчанию все) | Сводку вердиктов и подробности по первым `k` упавшим тестам (по умолчанию 2, с самым коротким входом): вход, правильный ответ, вывод программы, stderr |
| `get_test` | `name` | Вход и правильный ответ теста (с обрезкой) и их размеры |
| `run_program` | `code?`, `input` | stdout, stderr, код возврата, время |
| `trace` | `code?`, `test` или `input`, `lines`, `expressions`, `max_hits?` | Срабатывания: строка, номер прохода, значения выражений; вывод программы |
| `submit` | `code` | Прогон всех тестов. Все `AC` — решение принято, работа завершается. Иначе сводка вердиктов, можно продолжать. Каждый вызов — одна попытка, число попыток ограничено |

Если `code` не передан, используется исходная программа. Номера строк везде с 1.

## 7. LLM-клиент (`src/debugmas/llm/`)

- Используется официальная библиотека `openai` (`chat.completions.create`) с `base_url` и
  ключом из выбранного профиля — подходит любой OpenAI-совместимый сервер. Модель должна
  поддерживать tool calling. Если в одном ответе несколько вызовов инструментов, они
  выполняются по порядку.
- **Подсчёт токенов** берётся из `response.usage`: входные, выходные, токены рассуждений,
  закэшированные провайдером входные токены (если сервер их возвращает); сырой `usage`
  сохраняется целиком. Если сервер не вернул `usage`, токены **не оцениваются и не
  заменяются нулём**: запрос учитывается в счётчике `calls_without_usage` (для неудачных
  запросов с неизвестным расходом — `failed_without_usage`), и в отчёте видно, сколько
  таких запросов.
- **Повторы** при таймаутах, ошибке 429 и ошибках 5xx: с растущей задержкой, до
  `LLM_MAX_RETRIES` раз. Токены неудачных запросов, если сервер их сообщил, тоже
  учитываются. Если запрос так и не удался, задача получает статус `error`.
- **Кэш на диске** (`llm/cache.py`, SQLite). Повторный одинаковый запрос берётся из кэша,
  а не отправляется модели. Ключ кэша — хэш от адреса endpoint, модели, сообщений,
  инструментов, параметров генерации и номера повтора `repeat_idx` (чтобы можно было
  специально перезапустить без кэша). В кэше хранятся ответ, `usage` и исходная задержка.
  Ответ из кэша помечается
  `cache_hit: true`; токены и стоимость берутся из сохранённого `usage`, поэтому затраты
  считаются правильно. **Время решения** в отчёте учитывает только запросы не из кэша; для
  честного замера времени запускайте с выключенным кэшем.
- **Длина ответа ограничена** `llm.max_output_tokens` в конфиге (16384, одинаково для всех
  решателей). Без лимита модель с рассуждениями на трудной задаче может генерировать 100k+
  токенов около 10 минут на один запрос.
- **Таймаут на весь запрос** — `LLM_TIMEOUT_S` (300 с). Таймаут библиотеки `openai`
  считается между порциями данных, а OpenRouter держит соединение живым, пока модель
  думает, поэтому общий срок ограничивается отдельно; запрос, не уложившийся в него,
  повторяется как таймаут.
- **Рассуждения модели** задаются `llm.reasoning` в конфиге и передаются в запрос как есть
  (параметр `reasoning` OpenRouter). Сейчас отключены: `{enabled: false}`.
- Температура по умолчанию `0`.

## 8. Решатели

### 8.1. `workflow` (`solvers/workflow.py`)

Порядок действий задан в коде, модель инструменты не вызывает:

1. Программа готовит отчёт по исходным результатам: сводку вердиктов по всем тестам и
   подробности (вход, правильный ответ, вывод, stderr) для `k` упавших тестов с самым
   коротким входом.
2. **Попытка 1:** модель получает код с номерами строк и отчёт и возвращает исправленную
   программу целиком в блоке ```` ```python ````.
3. Программа берёт последний такой блок из ответа и прогоняет все тесты.
4. Если не все тесты `AC` — следующая попытка: модель получает свой последний вариант кода
   и новый отчёт (или сообщение о синтаксической ошибке, или «блок кода не найден»).
5. Не больше `max_attempts` попыток (по умолчанию 3).

Токены и время сохраняются **для каждой попытки отдельно** — по первой считается LLM-only.

Все данные, передаваемые модели: промпты, описания и ошибки инструментов, отчёты тестов
и подсказки трассировки — на английском. CLI и итоговые отчёты остаются русскоязычными.

Промпты: `prompts/workflow_system.md`, `prompts/workflow_retry.md`,
`prompts/feedback_no_code.md`, `prompts/feedback_syntax_error.md`.

### 8.2. `single_agent` (`solvers/single_agent.py`)

Цикл: модель → вызовы инструментов → результаты → снова модель.

- **Стартовое сообщение** — то же, что у `workflow` в первой попытке: код с номерами строк,
  сводка вердиктов, подробности по `k` упавшим тестам. Так у вариантов одинаковая стартовая
  информация (общий промпт `prompts/task_initial.md`).
- Инструменты: `run_tests`, `get_test`, `run_program`, `trace`, `submit`.
- Системный промпт `prompts/single_agent_system.md` описывает работу отладчика:
  воспроизвести ошибку → найти расхождение трассировкой → сформулировать причину →
  исправить → проверить → сдать.
- **Попытка** = вызов `submit`. Лимит попыток (`max_attempts`) тот же, что у `workflow`
  (по умолчанию 3).
- **Когда останавливается** и с каким статусом:

  | Статус | Причина |
  |---|---|
  | `solved` | `submit` принят |
  | `attempts_exhausted` | закончились попытки |
  | `step_limit` | достигнут `max_steps` (по умолчанию 30 ответов модели) |
  | `token_limit` | израсходован `max_tokens_per_task` (одинаков для всех решателей, по умолчанию 300 000) |
  | `error` | запрос к модели не удался или превышен таймаут задачи |

- Если модель ответила текстом без вызова инструмента, ей отправляется напоминание
  (`prompts/single_agent_reminder.md`); это считается шагом.
- Ошибки в аргументах инструментов возвращаются модели как результат инструмента с
  описанием ошибки — решатель из-за них не падает.
- **Сокращение контекста:** результаты инструментов старше последних 6 шагов заменяются
  короткой сводкой, например `[результат run_tests: 12 AC, 3 WA — сокращено]`.

### 8.3. Общий интерфейс (`solvers/base.py`)

Все решатели возвращают результат одинаковой формы, поэтому их можно сравнивать одним кодом.

```python
@dataclass
class Attempt:
    index: int                    # с 1
    code: str | None              # None — код не удалось извлечь
    verdicts: dict[str, str]      # имя теста -> вердикт
    passed_all: bool
    usage: Usage                  # workflow: токены этой попытки; single_agent: с начала работы до неё
    wall_time_s: float

@dataclass
class SolverResult:
    task_id: str
    solver: str
    status: str                   # solved | attempts_exhausted | step_limit | token_limit | error
    attempts: list[Attempt]
    final_code: str | None
    usage: Usage                  # итог по задаче, включая неудачные запросы
    wall_time_s: float
    llm_time_s: float
    sandbox_time_s: float
    steps: int
    tool_calls: dict[str, int]
    error: str | None

class Solver(Protocol):
    name: str
    def solve(self, view: AgentView, ctx: RunContext) -> SolverResult: ...
```

`RunContext` даёт решателю LLM-клиент, набор инструментов, лимиты и запись событий в
трассу. Решатели регистрируются через `register_solver`. **Решатели не импортируют
`GroundTruth` и не читают `ground_truth.json`** (раздел 12).

## 9. MAS

В `src/debugmas/solvers/mas/` реализован `mas_sequential`; `mas_competitive` запланирован:

- `mas_sequential`: исследователь сам выбирает вызовы `get_test`, `run_program`, `trace` и
  `run_tests`, затем передаёт вывод исправителю. Исправитель возвращает полную программу.
  Проверяющий обязательно запускает все тесты в песочнице; при провале кратко объясняет
  результат и возвращает его исследователю для следующего цикла. После успешной проверки
  дополнительный вызов модели не нужен. Каждый ответ исправителя считается одной попыткой,
  даже если из него не удалось извлечь код; в этом случае тесты не запускаются.
- `mas_competitive`: два исследователя получают одинаковую стартовую информацию, но ведут
  отдельные истории сообщений и вызовов инструментов. Первый ищет контрпример и граничные
  случаи, второй анализирует ход выполнения трассировкой. Каждый передаёт арбитру короткий
  структурированный вывод: гипотезу, свидетельства с указанием теста или наблюдения
  трассировки и предполагаемые строки ошибки. Допустим вывод «убедительной гипотезы нет».
  Арбитр видит только эти выводы; далее работают исправитель и проверяющий.

Если оба исследователя не нашли причину, они проводят один дополнительный цикл поиска с
другим фокусом, если остаётся общий бюджет. Если гипотезы различаются, арбитр может сделать
до двух целевых вызовов `get_test`, `run_program` или `trace`, чтобы проверить их. Исправителю
передаётся одна подтверждённая гипотеза, обе совместимые гипотезы либо обе с пометкой о
неопределённости. Вызовы арбитра входят в общий бюджет команды. Проверка гипотезы не считается
попыткой исправления: попытка — сдача кода на все тесты.

Оба решателя реализуют интерфейс `Solver`, возвращают `SolverResult` и используют существующие
инструменты из `tools/registry.py`. Максимум три попытки исправления на задачу, общий лимит
токенов, шагов и времени распространяется на всю команду. События в трассе содержат роль в поле
`agent`. Исследователи конкурирующей схемы не видят сообщения и результаты инструментов друг
друга до решения арбитра. Различие гипотез не гарантируется: независимость означает изоляцию
контекстов, а не обязательное расхождение ответов модели.

Изменения в общих модулях, нужные для MAS, вносятся отдельными коммитами вместе с
обновлением этого файла.

## 10. Эксперименты, метрики, отчёт

### 10.1. Запуск

`python -m debugmas run --config ... --split ...`:
- задачи решаются параллельно (до `LLM_MAX_CONCURRENCY` одновременно);
- результаты пишутся построчно, поэтому прерванный запуск **продолжается** с того же места
  повторной командой (`--resume`, включено по умолчанию);
- если решатель упал на одной задаче, остальные продолжаются, а эта задача получает
  `status=error`.

Результаты — в `results/<run_id>/`, где `run_id` = `<дата>_<solver>_<split>_<короткий хэш конфига и интерфейса модели>`.
Отпечаток включает промпты и код, формирующий сообщения модели, поэтому изменение языка или
формата инструкций создаёт новый запуск, а не продолжает прежний.

```
config.resolved.yaml   # итоговые настройки без секретов
meta.json              # git-коммит, есть ли незакоммиченные изменения, модель, хост endpoint, версии, время начала и конца
tasks.jsonl            # строка на задачу: SolverResult
trace.jsonl            # все события: входы и ответы модели, вызовы инструментов, попытки
candidates/<task_id>/attempt_<n>.py
metrics.json           # все метрики (раздел 10.2)
```

Пример события в трассе:

```json
{"run_id": "...", "task_id": "...", "solver": "single_agent", "agent": "single_agent",
 "step": 4, "event": "tool_call", "tool": "trace", "args": {}, "result": {},
 "usage": {"input": 812, "output": 154}, "cache_hit": false, "ts": "..."}
```

### 10.2. Метрики (`src/debugmas/eval/`)

Метрики взяты из лекции 6 курса («Качество, стоимость, задержка и бюджет»); номера слайдов
указаны в скобках. Единица наблюдения — **эпизод**: одна задача от получения до итогового
результата, со всеми попытками и неудачными запросами (14). Метрики считаются по **всем**
задачам выборки: `error` и остановка по лимиту — неудача, их расход и время входят в затраты.

**Качество:**
- `first_attempt_success` — первая попытка прошла все тесты (17). Первая попытка — первая
  сданная программа до исправлений по результатам её проверки: у `workflow` — первый ответ
  модели, у `single_agent` — первый `submit`;
- `final_success` — какая-либо попытка прошла все тесты (17);
- доли считаются по бинам сложности и по всему набору (16);
- **LLM-only** = первая попытка `workflow`, расход и время — только первой попытки;
- частичный результат — итоговая версия прошла часть тестов; статус остановки и качество
  хранятся отдельно (15);
- `fault_line_hit` — метрика нашей задачи (разрешена слайдом 8): итоговый патч меняет строку,
  где по разметке ConDefects была ошибка;
- парное сравнение на одних задачах: решили оба / только A / только B / никто и счёт 2/1/0 —
  победа 2 балла, ничья 1 каждому, поражение 0 (23–24);
- повторы одного варианта (несколько запусков с разным `repeat_idx`): успех запуска,
  стабильность (решена во всех повторах), хотя бы один успех (18).

**Причины провала** (19): решение (все попытки отклонены тестами), бюджет (лимит шагов,
токенов или времени), инфраструктура (сбой API или запуска), взаимодействие (сбой обмена
между агентами, для MAS).

**Затраты** (27–30):
- токены: вход без кэша, кэшированный вход, выход (включая рассуждения);
- стоимость = вход без кэша × тариф входа + кэшированный вход × тариф кэша + выход × тариф
  выхода; тарифы из `.env`. Инструменты локальные и бесплатные;
- цена эпизода = все расходы / число эпизодов;
- **стоимость успеха** = все расходы (включая неудачные эпизоды) / число успешных эпизодов;
  при нуле успехов не определена;
- запросы без `usage` и неудачные запросы с неизвестным расходом считаются отдельно, а не
  заменяются нулём.

**Время** (36–37): длительность эпизода — медиана, p95 и максимум по правилу ближайшего ранга
(значение с номером ceil(q·n) в отсортированном ряду) и число наблюдений.

**Выбор конфигурации** (38–39): доля успехов вместе с ценой эпизода и p95; Парето-фронт —
варианты, для которых нет другого варианта не дороже и не хуже по успеху.

**Проверка подгонки под тесты.** Решатель видит все тесты, поэтому может подогнать программу
под конкретные ответы. `eval/patch_analysis.py` помечает итоговый патч как подозрительный
(`suspicious`), если он добавляет константы, совпадающие с ожидаемыми ответами тестов;
сравнивает вход с конкретными значениями из тестов; обращается к файлам, сети, `os`,
`subprocess`; слишком большой (больше 10 строк). Результат пишется в `metrics.json` для ручной
проверки и в сравнение не входит.

`eval/metrics.py` меняется только отдельным коммитом с пояснением, после чего все отчёты
пересчитываются.

### 10.3. Отчёт (`make report`)

`report.md` и графики пишутся в `results/reports/<дата>/`. Графики строятся через plotly
(`report/charts.py`): `.png` встраивается в отчёт, рядом лежит интерактивный `.html`.
Все цифры остаются в `metrics.json` запусков.

Для совместного отчёта `workflow`, `single_agent` и `mas_sequential` до записи файлов
проверяются совпадение ID задач, каталога данных, выборки, границ сложности, модели,
endpoint, параметров вызовов, тарифов, интерфейса модели, лимитов и стартовой информации. Несовпадение
останавливает построение отчёта с ошибкой.

Разделы отчёта (по требованиям к показу, слайд 8):
1. **Условия сравнения** (21) — критерий успеха и граница первой попытки; задачи (число по
   бинам и точные идентификаторы); model ID и параметры вызовов; инструменты; лимиты и
   фактический расход; коммит. Если условия запусков различаются — предупреждение.
2. **Качество** — итоговый успех по бинам и в целом, успех с первой попытки, частичный
   результат, `fault_line_hit`; парное сравнение со счётом 2/1/0; повторы, если есть.
   График итогового успеха по бинам.
3. **Затраты и время** — токены по категориям, стоимость всего, цена эпизода, стоимость
   успеха, неудачные запросы и запросы без `usage`, время эпизода (медиана / p95 / максимум).
   Парето-фронт и его график.
4. **Успехи и провалы** — причины провала по вариантам и задачи для разбора: агент решил, а
   `workflow` нет, и наоборот; все варианты провалились; остановки по лимиту и сбои.

`make case RUN=... TASK=...` печатает историю решения одной задачи: исходный код с отмеченной
строкой ошибки (из `GroundTruth`, только в отчёте), каждый ответ модели, вызовы инструментов
с сокращёнными результатами, попытки и вердикты, итоговый diff и diff с эталоном.

## 11. Как усложнить задачу, если агент справляется слишком легко

Всё меняется в конфиге, без переписывания кода:

| Что менять | Где | Эффект |
|---|---|---|
| Пресет и бины сложности | `configs/splits.yaml`, `bins` в конфиге запуска | Только сложные задачи |
| Модель | `MODEL` в выбранном профиле | Более слабая модель |
| Сколько упавших тестов показать в начале | `initial_failing_shown` | 0 — только сводка вердиктов, подробности агент запрашивает сам |
| Показывать ли правильный ответ | `show_expected_output` | Агент видит только вердикт и свой вывод |
| Лимиты | `max_attempts`, `max_steps`, `max_tokens_per_task` | Меньше бюджета |
| Набор инструментов | `tools: [...]` | Например, агент без `trace` |

На будущее (сейчас не делается): режим с условиями задач и скрытыми тестами, переименование
переменных в коде, добавление второй ошибки.

## 12. Жёсткие правила

1. **Решатели не видят эталон (`GroundTruth`).** Его используют только `eval/`, `report/`
   и `data/`. Модули `solvers/`, `tools/`, `llm/`, `sandbox/` не импортируют `GroundTruth`
   и не читают `ground_truth.json`. Это проверяет `tests/test_no_leakage.py` — не удаляйте
   и не ослабляйте его.
2. **Чужой код запускается только в песочнице** (раздел 6.1).
3. **Таймауты везде:** на тест, трассировку, запрос к модели, задачу.
4. **Одинаковые условия:** модель, температура, `max_attempts`, `max_tokens_per_task` и
   стартовая информация одинаковы для всех решателей в одном сравнении. Конфиги для
   сравнения отличаются только `solver` и параметрами конкретного решателя.
5. **Промпты настраиваются только на `dev`.** После изменения промпта все затронутые
   решатели заново прогоняются на `val`.
6. **Выборка `test` — только через `make final`** (раздел 5.3).
7. **Не коммитить** рабочие `.env` и `.env.*`, `data/`, `results/`, `.cache/`.
   **Коммитить** шаблоны `.env.*.example`, `splits/`, `configs/`, `prompts/`, `docs/`.
8. Метрики в `eval/metrics.py` меняются только отдельным коммитом с пояснением, после чего
   пересчитываются все отчёты.

## 14. Тесты проекта

- **Фикстуры** `tests/fixtures/condefects_mini/` — 7 игрушечных задач в той же структуре,
  что ConDefects (раздел 4.1). Среди них: программа с бесконечным циклом, с исключением, с
  выводом вещественных чисел, с решением в отдельном потоке, и задачи, которые должны
  отсеяться при проверке. Тесты никогда не скачивают ConDefects и не ходят в сеть.
- **Фейковая LLM** `llm/fake.py` выдаёт заранее заданную последовательность ответов (текст
  или вызовы инструментов) с фиктивным `usage`. Через неё тестируются оба решателя, подсчёт
  токенов, лимиты и отчёт. Сценарии для smoke — в `tests/fixtures/condefects_mini/fake_llm.yaml`.

Что покрыто тестами:

| Модуль | Проверки |
|---|---|
| `sandbox` | AC/WA/RE/TLE/MLE, обрезка вывода, изоляция рабочей папки, погрешность для чисел |
| `tracer` | значения до выполнения строки, `max_hits`, ошибки вычисления выражений, потоки, `exit()`, таймаут с частичным результатом |
| `data` | разбор фикстур, причины отсева, одна программа на задачу |
| `splits` | повторяемость при одном seed, непересечение выборок, равное число задач из каждого бина, пресеты |
| защита `test` | `run --split test` отклоняется; `final` отклоняется при незакоммиченных изменениях и существующем теге |
| `llm` | кэш (попадание/промах, ключ учитывает `repeat_idx`), повторы при 429/5xx, токены при ошибках, запросы без `usage` считаются, а не оцениваются |
| `workflow` | извлечение блока кода, нет блока, синтаксическая ошибка, успех со 2-й попытки, токены по попыткам |
| `single_agent` | ошибочные аргументы инструмента, ответ без вызова инструмента, принятый и отклонённый `submit`, все лимиты, сокращение контекста |
| `eval` / `report` | метрики на примерах из лекции 6 (первая попытка, стоимость успеха, квантили, парный счёт, повторы, Парето), `error` считается неудачей и входит в затраты, `fault_line_hit`, `suspicious` |
| утечка эталона | `test_no_leakage.py` |
| end-to-end | `make smoke` для обоих решателей создаёт полный набор файлов результатов и отчёт |

Тест с настоящей моделью помечен `@pytest.mark.live` и по умолчанию пропускается
(запуск: `pytest -m live`).

## 15. Стиль кода

- Python 3.11, аннотации типов во всём `src/`, `dataclasses` или `pydantic` для структур.
- `ruff check` и `ruff format` — без ошибок перед коммитом (`make test` это проверяет).
- Логирование через `logging`; `print` только в CLI.
- Все случайные выборы — через seed из конфига, чтобы результаты повторялись.
- Небольшие модули с одной задачей. Новые инструменты, решатели и метрики добавляются через
  реестры, а не через `if` в общем коде.
- Тексты для модели лежат только в `prompts/` и не дублируются в коде.
