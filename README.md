# debugmas — LLM-отладчик Python-программ

Учебный проект по курсу «Мультиагентные системы».

## Что мы делаем

Берём небольшую программу на Python с ошибкой: решение задачи с соревнований AtCoder,
которое на части тестов выдаёт неверный ответ. Отдаём её языковой модели (LLM) и смотрим,
сможет ли модель найти и исправить ошибку.

Нас интересует не просто «умеет или нет», а **какой способ организовать работу модели
лучше**. Поэтому одну и ту же задачу решают несколько вариантов системы, и мы сравниваем,
сколько задач каждый исправил и сколько это стоило.

Программы с ошибками берём из открытого набора данных
[ConDefects](https://github.com/appmlk/ConDefects). Для каждой программы там известны:
сама программа с ошибкой, исправленная версия, номер строки с ошибкой и тесты (входные
данные и правильные ответы).

## Как выглядит одна задача

Модель получает:
- программу с ошибкой (строки пронумерованы);
- результаты прогона этой программы на тестах: какие тесты прошли, какие нет;
- для пары упавших тестов — вход, правильный ответ и что выдала программа.

Условия задачи у модели нет — что программа должна делать, понятно только из тестов.

Модель должна вернуть исправленную программу. **Задача считается решённой, если исправленная
программа проходит все тесты.**

Пример: в программе написано `for i in range(1, n):`, а нужно `range(1, n + 1)`. Тест с
`n = 5` ждёт ответ `15`, программа выдаёт `10`. Модель должна это заметить и поправить строку.

## Какие варианты сравниваем

| Вариант | Как работает | Аналогия |
|---|---|---|
| **LLM-only** | Один запрос к модели: «вот код и упавшие тесты, исправь». Без второй попытки | Студент сдаёт работу с первого раза, без проверки |
| **workflow** | То же, но если исправление не прошло тесты, программа сама отправляет модели результаты проверки и просит попробовать ещё раз (до 3 попыток). Порядок действий жёстко задан в коде | Студент получает от преподавателя «не прошло, вот ошибки» и переделывает |
| **single_agent** | Модель сама решает, что делать: запустить тесты, запустить программу на своём примере, посмотреть значения переменных по ходу выполнения, и когда сдавать ответ | Программист, который сам пользуется отладчиком |
| **mas_sequential** | Исследователь выбирает инструменты, исправитель предлагает код, проверяющий запускает тесты и объясняет неудачу | Команда с последовательными ролями |
| **mas_competitive** *(в планах)* | Два независимых исследователя предлагают гипотезы; арбитр проверяет их перед исправлением | Команда с конкурирующими гипотезами |

LLM-only отдельно не запускается: это просто первая попытка варианта workflow.

## Что получаем на выходе

Отчёт `report.md` с таблицами и графиками:
1. **Условия** — на каких задачах, какой моделью и с какими ограничениями сравнивали.
2. **Качество** — какую долю задач исправил каждый вариант, отдельно для лёгких,
   средних и сложных задач.
3. **Затраты** — сколько токенов, денег, времени и шагов ушло на одну задачу.
4. **Что разобрать вручную** — задачи, где один вариант справился, а другой нет, и
   задачи, которые не решил никто.

## Словарик

| Термин | Что значит |
|---|---|
| **Решатель** (solver) | Один из вариантов системы: `workflow`, `single_agent`, `mas_sequential`; `mas_competitive` пока в планах |
| **Попытка** | Одна сданная моделью исправленная программа. Число попыток ограничено (по умолчанию 3) |
| **Шаг** | Один ответ модели. У `single_agent` и `mas_sequential` ограничено число шагов на задачу (по умолчанию 30) |
| **Инструменты** (tools) | Действия, которые single_agent может вызывать: прогнать тесты, посмотреть тест, запустить программу, трассировка, сдать ответ |
| **Трассировка** | Запуск программы с записью значений переменных на указанных строках — как отладчик, но без ручного управления |
| **Песочница** | Изолированный запуск чужого кода с ограничениями по времени и памяти, чтобы программа не могла навредить системе |
| **Вердикт** | Результат одного теста: `AC` — верно, `WA` — неверный ответ, `RE` — программа упала, `TLE` — превышено время, `MLE` — превышена память |
| **Бин сложности** | Группа задач по сложности (easy / medium / hard). Сложность берётся из ConDefects |
| **Выборки** dev / val / test | Три непересекающихся набора задач: `dev` — для разработки и отладки, `val` — для промежуточных сравнений, `test` — закрытый, только для финальных результатов |
| **Токены** | Единицы текста, за которые платим модели. Учитываем входные (что отправили) и выходные (что модель написала) |
| **Ground truth** | Правильный ответ из разметки: исправленная программа и номер строки с ошибкой. Модели не показывается, нужен только для оценки |

## С чего начать

Нужны Docker и `make`. Все команды выполняются внутри контейнера.

```bash
cp .env.example .env          # вписать адрес модели, ключ и цены
make build                    # собрать Docker-образ
make test                     # проверки кода и тесты (без сети)
make smoke SOLVER=workflow    # пробный прогон на 5 игрушечных задачах, без настоящей модели
make smoke SOLVER=mas_sequential  # те же задачи с последовательной MAS
```

`make smoke` — самый быстрый способ увидеть, как всё работает: он создаёт папку результатов
и отчёт в `results/smoke/`. Цифры в этом отчёте ненастоящие: задачи игрушечные, а ответы
«модели» заранее записаны.

Для разных провайдеров скопируйте нужный шаблон в файл без `.example`:

```bash
cp .env.openrouter.example .env.openrouter  # прямой OpenRouter
cp .env.local.example .env.local            # локальный OpenAI-совместимый сервер
```

Заполните ключ в `.env.openrouter` и сверьте модель и тарифы со
[страницей DeepSeek V4.1 Flash](https://openrouter.ai/deepseek/deepseek-v4.1-flash).
Для локального сервера укажите его модель в `.env.local`. Если используете прокси к
OpenRouter, замените адрес
в `.env.openrouter` на адрес прокси и проверьте ID модели. Оба файла игнорируются Git.
`make run PROFILE=openrouter ...`
использует `.env.openrouter`, `PROFILE=local` — `.env.local`, а без `PROFILE`
сохраняется прежний `.env`. В одном сравнении всех решателей используйте один профиль.
Ключ не записывается в конфигурацию результатов. Платные запуски требуют отдельного
согласования.

### Откуда берутся данные

Данные в репозиторий не коммитятся, каждый скачивает их сам в `data/raw/`.

| Что | Откуда | Зафиксировано? |
|---|---|---|
| Программы с ошибками, исправленные версии, строка ошибки, сложность и дата задач | [github.com/appmlk/ConDefects](https://github.com/appmlk/ConDefects) | Да: коммит в `configs/data.yaml` |
| Тесты (основной способ) | Зеркало официальных тестов AtCoder [github.com/conlacda/atcoder-testcases](https://github.com/conlacda/atcoder-testcases), по ветке на контест; качает `make fetch-tests` | Нет: качается текущее состояние веток. Контеста `abc317` в зеркале нет (6 задач отсеются) |
| Тесты (запасной способ) | `Test.zip` авторов ConDefects: ссылки OneDrive и Baidu в [README ConDefects](https://github.com/appmlk/ConDefects#test-cases-download). Положить в `data/raw/Test.zip` | Да, но скачивается только вручную через браузер |
| Библиотеки для запуска программ | PyPI, список в `requirements-atcoder.txt` | Нет: версии не указаны |

### Подготовка настоящих данных

```bash
make fetch-tests          # ConDefects + тесты в data/raw/ (десятки минут; можно прервать и продолжить)
make data                 # проверка программ, результат в data/processed/ (долго, см. ниже)
make split PRESET=paper3  # выборки dev / val / test в splits/ (коммитятся)
```

Для пилота из шести задач выполните:

```bash
make data ARGS='--out data/pilot/final --task abc223_a --task abc224_b --task abc223_d --task abc225_d --task abc223_e --task abc223_f'
```

Список задач сохранён в `splits/pilot/paper3/dev.txt`: по две лёгкие, средние и сложные.
Они закреплены за `dev` при будущем полном разбиении. Для запуска решателей используйте
`--set data_dir=data/pilot/final --set splits_dir=splits/pilot` в `make run ARGS=...`.
Можно передавать по одному `--task <id>` с тем же конфигом: задачи добавятся в один
продолжаемый запуск. Его `trace.jsonl` сохраняет входы и ответы модели, вызовы
инструментов и попытки для каждой задачи; каталог `results/` игнорируется Git.
Проверка исходных программ не вызывает LLM. Значение `unknown` в `difficulty.txt`
исключает задачу при подготовке.

| Сложность | Задачи (рейтинг; число тестов) |
|---|---|
| Лёгкие | `abc223_a` (6; 14), `abc224_b` (81; 30) |
| Средние | `abc225_d` (778; 25), `abc223_d` (1069; 22) |
| Сложные | `abc223_e` (1510; 48), `abc223_f` (1641; 33) |

Это пилотный набор для отладки; результаты на шести задачах предварительные.

### Быстрый пилот на 30 задачах

Для следующего сравнения используется `splits/pilot30/paper3/dev.txt`: 10 лёгких, 10 средних
и 10 сложных задач. Скрипт сохраняет шесть задач малого пилота, а остальные детерминированно
выбирает из локально доступных Python-задач ConDefects с тестами (`seed=42`) и сразу записывает
фиксированный список из 30 ID. Быстрая подготовка проверяет только выбранные ошибочные версии:
исправленные версии не запускаются, а задача с уже проходящей версией переключается на следующую.
Подготовленные данные остаются в игнорируемом `data/pilot/pilot30/`; список задач следует
добавить в Git после успешной подготовки.

```bash
make prepare-pilot30
make run-pilot30 PILOT_ARGS=--dry-run  # показывает 30 × 3 запусков, без запросов к модели
make run-pilot30            # требует локальный .env.openrouter
```

Запуск идёт последовательно: `workflow`, `single_agent`, `mas_sequential` для одной задачи,
после чего переходит к следующей. Он продолжает существующие результаты в
`results/pilot30_live/`, выводит накопленные токены, стоимость, время и успешные задачи после
каждой тройки. Перед новой задачей он останавливается, если наблюдаемая суммарная стоимость
достигла `$2.00`; уже начатая тройка может немного превысить этот порог.

Все варианты используют одинаковые настройки: `max_tokens_per_task=60000`, до трёх попыток,
до 30 шагов, таймаут 900 секунд, четыре начальных упавших теста, 8 000 символов ответа
инструмента, 12 сохраняемых шагов контекста, `max_output_tokens=4096`, `temperature=0`,
выключенные reasoning и LLM-кэш. Это быстрый предварительный пилот на выборке `dev`, а не
финальный `test`.

- `make fetch-tests` сам клонирует ConDefects на нужном коммите, затем качает тесты только
  для задач на Python. При повторном запуске пропускает уже скачанное.
- `make data` проверяет каждую программу и оставляет по одной на задачу. Что отброшено и
  почему — в `data/processed/validation_report.json`. Если там есть причины
  `missing_library:<имя>`, допишите библиотеку в `requirements-atcoder.txt` и повторите
  `make build` и `make data`.
- Если вместо `make fetch-tests` используете `Test.zip`, положите его в `data/raw/Test.zip`
  и запускайте сразу `make data`.

### Известные ограничения (будут исправлены)

- **Тесты не закреплены по версии.** Зеркало может измениться или пропасть. План: записать
  коммит каждой ветки и контрольные суммы тестов.
- **Результат `make data` зависит от машины.** Задачи, где исправленная версия не уложилась
  во время, отсеиваются, а лимиты времени считаются по замеру. На разных машинах набор задач
  может немного отличаться. План: один раз проверить данные и закоммитить «снимок» (какие задачи
  и программы оставлены, лимиты), а на других машинах собирать данные по нему.
- **Версии библиотек песочницы не закреплены.** План: прописать версии в
  `requirements-atcoder.txt`.
- **`make data` долгий:** по замеру — несколько часов на полный набор. План: прекращать проверку
  на первом упавшем тесте и проверять задачи параллельно.

### Запуск сравнения

```bash
make run CONFIG=configs/workflow.yaml SPLIT=val
make run CONFIG=configs/single_agent.yaml SPLIT=val
make run CONFIG=configs/mas_sequential.yaml SPLIT=val
make report RUNS="results/<workflow> results/<single_agent> results/<mas_sequential>"
make case RUN=results/<папка_запуска> TASK=<id_задачи>   # пошаговая история одной задачи
```

Если запуск прервался, повторите ту же команду: уже решённые задачи пропускаются.
Для отчёта с тремя архитектурами нужны одинаковые задачи, каталог данных, модель,
параметры вызовов, тарифы и общие лимиты. При расхождении `make report` остановится
с пояснением, какие условия различаются. `mas_sequential` включён в разбор случаев.
Выборка `test` запускается только через `make final` и только из чистого (закоммиченного)
состояния репозитория — чтобы финальные цифры были честными.

### Результаты пилота для визуализатора

В `tests/fixtures/run_outputs/english_pilot/` сохранены без изменений полные каталоги трёх
фактических английских запусков пилота: `workflow`, `single_agent` и `mas_sequential`.
Они содержат конфигурацию, метаданные, метрики, результаты всех шести задач, трассу и
предложенные исправления. Эти данные можно использовать для разработки и отладки будущего
визуализатора; их исходные рабочие копии по-прежнему лежат в игнорируемом `results/`.

## Важные правила

- Модель **никогда** не видит правильный ответ (ground truth). Это проверяет тест
  `tests/test_no_leakage.py`.
- Код от модели и из датасета запускается **только** в песочнице.
- Промпты меняем и проверяем только на выборке `dev`, на `test` ничего не отлаживаем.
- Варианты сравниваем при одинаковых условиях: та же модель, те же лимиты, те же задачи.

Правила работы — в [AGENTS.md](AGENTS.md), подробная спецификация — в [docs/spec.md](docs/spec.md).
